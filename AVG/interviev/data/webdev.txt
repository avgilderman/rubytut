Вопросы по веб-разработке

Вопрос 1. Что происходит после того, как вы вводите название сайта в браузер и нажимаете Enter? Подробно объяснить.

Ответ 

#### *1. Парсинг URL - можно отнести к условно первому этапу (не считая самого процесса ввода символов в поисковом поле браузера), во время которого*:
- Браузер проверяет список предзагруженных HSTS (HTTP Strict Transport Security). Это список сайтов, которые требуют, чтобы к ним обращались только по HTTPS. Если нужный сайт есть в этом списке, то браузер отправляет ему запрос через HTTPS вместо HTTP. В противном случае, начальный запрос посылается по HTTP.
- Конвертируются не-ASCII Unicode символы в название хоста.

#### *2. Следующий этап - Определение DNS*
- Браузер проверяет наличие домена в своём кэше. Если домена там нет, то браузер вызывает библиотечную функцию *gethostbyname* (отличается в разных ОС) для поиска нужного адреса в файле *hosts*.
- Если домен нигде не закэширован и отсутствует в файле hosts, gethostbyname отправляет запрос к сетевому DNS-серверу.
- Запрос к сетевому DNS-серверу называется ARP-запросом.
- Для того, чтобы отправить ARP-запрос браузеру необходимо отыскать целевой IP-адрес, а также знать MAC-адрес интерфейса, который будет использоваться для отправки ARP-запроса.

#### *3. Открытие сокета и сборка TCP-сегмента/пакета*
- Когда браузер получает IP-адрес конечного сервера, то он берёт эту информацию и данные об используемом порте из URL (80 порт для HTTP, 443 для HTTPS), осуществляет вызов функции socket системной библиотеки и запрашивает поток TCP сокета.
- Этот запрос сначала проходит через транспортный уровень, где собирается TCP-сегмент. Получившийся сегмент отправляется на сетевой уровень, на котором добавляется дополнительный IP-заголовок, IP-адрес сервера назначения и адрес текущей машины — теперь сегмент сформирован.

#### *4. TLS handshake — для передачи пакетов данных между клиентом (компьютером) и сервером важно установить TCP-соединение. Это соединение устанавливается с помощью процесса, называемого трехсторонним рукопожатием TCP / IP, реализованного следующим образом*:

- Клиентская машина отправляет SYN-пакет на сервер, спрашивая, открыт ли он для новых подключений.
- Если на сервере есть открытые порты, которые могут принимать и инициировать новые соединения, он ответит, используя пакет SYN / ACK.
- Клиент получит пакет SYN / ACK от сервера и подтвердит его, отправив пакет ACK.

#### *5. Обработка HTTP-запросов на сервере*
- Одним из инструментов обработки запросов/ответов на стороне сервера является  HTTPD. Наиболее популярные HTTPD-серверы это Apache или Nginx для Linux и IIS для Windows.
- Сервер разбирает запрос по следующим параметрам: метод HTTP-запроса (наиболее распространенные — GET/POST), домен, запрашиваемые пути.
- Сервер находит контент, который соответствует запросу и парсит файл с помощью обработчика.

#### *6. Парсинг HTML и интерпретация CSS*
- Главной задачей HTML-парсера является разбор разметки в специальное дерево — «parse tree» — это дерево DOM-элементов.
- Во время разбора браузер парсит CSS-файлы, каждый из которых разбирается в объект StyleSheet.

#### *7. Рендеринг страниц и пост-рендеринговое исполнение*
- Путём перебора DOM-узлов и вычисления для каждого узла значений CSS-стилей создаётся «Дерево рендера» (Render Tree или Frame Tree).
- Вычисляются координаты каждого узла. Вычисляются финальные позиции слоёв и через Direct3D/OpenGL отдаются композитные команды.
- После завершения рендеринга, браузер исполняет JavaScript-код в результате срабатывания  часового механизма или в результате действий пользователя.

Вопрос 2. Что такое сессия? Для чего используется?
Ответ
Сессия — это механизм для сохранения состояния пользователя между его запросами к веб-приложению, так как HTTP — протокол без сохранения состояния (stateless).
Как работает:

При первом запросе сервер создаёт уникальный идентификатор сессии (session ID), который отправляется клиенту (обычно в виде cookie).
Клиент отправляет этот ID с каждым последующим запросом, позволяя серверу идентифицировать пользователя и связать с ним данные.
Данные сессии хранятся на сервере (например, в памяти, базе данных или файлах) или на клиенте (в cookie).

Для чего используется:

Аутентификация: Хранение информации о входе пользователя (например, "залогинен/не залогинен").
Персонализация: Сохранение пользовательских настроек (например, язык интерфейса).
Корзина покупок: Отслеживание товаров в интернет-магазине.
Состояние приложения: Сохранение промежуточных данных (например, прогресс заполнения формы).

Пример:
В Ruby on Rails сессия может храниться в cookie:
rubysession[:user_id] = user.id # Сохранение ID пользователя
Клиент получает cookie с session_id, а сервер сопоставляет его с данными.
Особенности:

Безопасность: Сессии должны быть защищены (например, через HTTPS, защиту от CSRF).
Ограничения: Сессии могут увеличивать нагрузку на сервер, если хранятся в памяти или базе данных.

Вопрос 3. Что такое процессы? Как с ними работать?
Ответ
Процессы — это экземпляры программ, выполняющихся в операционной системе. В контексте веб-разработки процессы представляют собой экземпляры веб-сервера, приложения или фоновых задач, которые обрабатывают запросы или выполняют вычисления.
Как работают процессы:

Каждый процесс имеет собственное адресное пространство, ресурсы (память, CPU) и выполняется независимо.
Веб-серверы (например, Nginx, Puma) могут запускать несколько процессов для обработки параллельных запросов.
Процессы обмениваются данными через механизмы IPC (Inter-Process Communication), например, сокеты или файлы.

Работа с процессами:

Запуск:

Процессы запускаются через командную строку, скрипты или менеджеры процессов (например, systemd, pm2).
Пример: Запуск сервера Puma в Ruby on Rails:
bashpuma -w 4 # Запускает 4 рабочих процесса



Управление:

Мониторинг: Используйте ps, top, htop для просмотра активных процессов.
Остановка: Используйте kill <pid> или pkill <name> для завершения процесса.
Ограничение ресурсов: Настройка через ulimit или конфигурации ОС.


Масштабирование:

Запуск нескольких процессов для обработки нагрузки (например, рабочие процессы в Puma или Gunicorn).
Использование менеджеров процессов, таких как pm2 для Node.js:
bashpm2 start app.js --name my-app -i 4 # 4 процесса



Фоновые задачи:

Процессы для фоновых задач (например, Sidekiq для Ruby или Celery для Python).
bashbundle exec sidekiq # Запуск фонового процесса




Особенности:

Процессы изолированы, что повышает надёжность, но увеличивает потребление памяти.
Для масштабируемости часто используются потоки (threads) внутри процессов или контейнеры (Docker).

Вопрос 4. Что такое DNS?
Ответ
DNS (Domain Name System) — это система, которая преобразует доменные имена (например, example.com) в IP-адреса (например, 192.0.2.1), понятные компьютерам.
Как работает:

Пользователь вводит домен в браузере.
Браузер запрашивает DNS-сервер (например, 8.8.8.8 от Google).
DNS-сервер возвращает IP-адрес, связанный с доменом, через цепочку запросов:

Корневые серверы → TLD-серверы (.com, .org) → Авторитетные серверы домена.


Браузер использует IP-адрес для связи с сервером.

Типы записей DNS:

A: Доменное имя → IPv4-адрес.
AAAA: Доменное имя → IPv6-адрес.
CNAME: Псевдоним одного домена для другого.
MX: Серверы для обработки почты.
TXT: Текстовые записи (например, для верификации).

Пример:
bashnslookup example.com
# Ответ: 93.184.216.34
Для чего используется:

Упрощение доступа к сайтам (домены вместо IP).
Балансировка нагрузки (CNAME для распределения трафика).
Настройка почты и других сервисов.

Вопрос 5. Настройка http-серверов.
Ответ
HTTP-сервер — это программа, которая принимает HTTP-запросы от клиентов (браузеров) и возвращает ответы (HTML, файлы, API-ответы). Примеры: Nginx, Apache, Puma.
Основные шаги настройки:

Установка:

Установите сервер через пакетный менеджер:
bashsudo apt install nginx # Для Ubuntu
sudo yum install httpd # Apache на CentOS



Конфигурация:

Файлы конфигурации:

Nginx: /etc/nginx/nginx.conf или /etc/nginx/sites-available/.
Apache: /etc/httpd/conf/httpd.conf или /etc/apache2/sites-available/.


Пример конфигурации Nginx:
nginxserver {
listen 80;
server_name example.com;
location / {
root /var/www/html;
index index.html;
}
}

Пример Apache:
apache<VirtualHost *:80>
ServerName example.com
DocumentRoot /var/www/html
<Directory /var/www/html>
AllowOverride All
</Directory>
</VirtualHost>



Запуск и перезапуск:

Nginx: sudo systemctl start nginx, sudo nginx -s reload.
Apache: sudo systemctl start httpd, sudo systemctl reload httpd.


Настройка безопасности:

Включение HTTPS (SSL/TLS) с помощью Let’s Encrypt:
bashsudo certbot --nginx # Автоматическая настройка SSL для Nginx

Ограничение доступа: Используйте файрвол (ufw) или правила в конфигурации.


Логирование и мониторинг:

Логи: /var/log/nginx/access.log (Nginx) или /var/log/httpd/access_log (Apache).
Используйте инструменты вроде Prometheus или Grafana для мониторинга.



Особенности:

Проксирование: Nginx часто используется как обратный прокси для передачи запросов к Puma или Node.js.
Статические файлы: Nginx и Apache оптимизированы для отдачи статических файлов (CSS, JS, изображения).
Динамический контент: Для приложений (Ruby, Python) используются серверы вроде Puma, интегрированные через прокси.

Вопрос 6. Сравните сервер аппликейшены и сервис апликейшены (Nginx, Apache, Puma, Webrick).
Ответ
Серверные приложения (Application Servers):

Примеры: Puma, Webrick, Gunicorn, Unicorn.
Назначение: Выполняют серверный код (Ruby, Python, Node.js), обрабатывают бизнес-логику, взаимодействуют с базами данных.
Особенности:

Работают с динамическим контентом (генерация HTML, API).
Обычно не оптимизированы для отдачи статических файлов.
Поддерживают многопоточность или многопроцессность (например, Puma использует потоки).
Пример: Puma для Ruby on Rails:
bashbundle exec puma -t 4:16 # 4-16 потоков



Плюсы:

Гибкость для обработки сложной логики.
Простая интеграция с фреймворками (Rails, Django).


Минусы:

Медленнее для статических файлов.
Высокое потребление ресурсов при больших нагрузках.



Сервисные приложения (Web Servers):

Примеры: Nginx, Apache.
Назначение: Обрабатывают HTTP-запросы, отдают статические файлы, выступают как прокси или балансировщики нагрузки.
Особенности:

Оптимизированы для обработки большого количества HTTP-запросов.
Часто используются как обратный прокси для передачи запросов к серверным приложениям.
Поддерживают кэширование, сжатие, SSL.
Пример: Nginx как прокси для Puma:
nginxserver {
listen 80;
server_name example.com;
location / {
proxy_pass http://localhost:3000; # Puma
}
}



Плюсы:

Высокая производительность для статического контента.
Хорошая масштабируемость.
Простота настройки HTTPS и балансировки.


Минусы:

Не предназначены для выполнения серверного кода.
Меньшая гибкость для сложной логики.



Сравнение конкретных серверов:

Сервер,Тип,Плюсы,Минусы,Использование
Nginx,Веб-сервер,"Высокая производительность, низкое потребление памяти, отличный прокси",Сложнее для динамического контента,"Статические файлы, прокси, балансировка"
Apache,Веб-сервер,"Гибкость модулей, простота настройки",Выше потребление ресурсов,Универсальный веб-сервер
Puma,Сервер приложений,"Поддержка потоков, интеграция с Rails",Не оптимизирован для статических файлов,Ruby on Rails приложения
Webrick,Сервер приложений,"Простота, встроен в Ruby","Низкая производительность, не для продакшена",Тестовые среды в Ruby

Когда использовать:

Nginx/Apache: Для отдачи статических файлов, проксирования, HTTPS, балансировки.
Puma/Webrick: Для выполнения серверного кода в Ruby-приложениях. Puma подходит для продакшена, Webrick — для разработки.
Комбинация: Nginx/Apache как прокси + Puma/Gunicorn для обработки логики.

Вопрос 7. Nginx, его отличие от apache?


Ответ 
Два самых широко распространенных веб-сервера. Если рассматривать жизненные примеры, то основные различия между Apache и Nginx в том как они обрабатывают запросы к статическому и динамическому контенту.


Вопрос 8. Почему используют не Puma, а Nginx?
Ответ
Puma и Nginx выполняют разные роли в веб-разработке, и их использование зависит от задач. Nginx часто предпочитают в продакшене не вместо Puma, а в связке с ним, потому что они решают разные проблемы. Вот основные причины, почему используют Nginx вместо или вместе с Puma:
Различия в назначении:

Nginx:

Это веб-сервер, оптимизированный для обработки HTTP-запросов, отдачи статического контента (HTML, CSS, JS, изображения) и управления сетевыми соединениями.
Используется как обратный прокси (reverse proxy) для передачи запросов к серверу приложений (например, Puma) или как балансировщик нагрузки.
Основные задачи:

Обработка большого количества одновременных соединений с низким потреблением памяти.
Эффективная отдача статических файлов.
Настройка HTTPS (SSL/TLS), кэширование, сжатие ответов.
Балансировка нагрузки между несколькими серверами приложений.




Puma:

Это сервер приложений, предназначенный для выполнения серверного кода (например, Ruby on Rails) и обработки динамического контента (логика приложения, взаимодействие с базой данных).
Основные задачи:

Выполнение Ruby-кода.
Обработка запросов, требующих бизнес-логики (например, генерация HTML-страниц, API-ответов).
Поддержка многопоточности или многопроцессности для параллельных запросов.





Почему выбирают Nginx вместо Puma (или в дополнение):

Производительность для статического контента:

Nginx значительно быстрее и эффективнее отдаёт статические файлы (CSS, JS, изображения), так как оптимизирован для работы с файловой системой и сетевыми соединениями.
Puma не предназначен для этого и тратит больше ресурсов на обработку статических файлов.


Обработка большого числа соединений:

Nginx использует асинхронную, событийно-ориентированную модель (event-driven), что позволяет ему обрабатывать тысячи одновременных соединений с минимальным потреблением памяти.
Puma, напротив, использует потоки или процессы, которые потребляют больше ресурсов при масштабировании.


Обратный прокси и балансировка:

Nginx может выступать как прокси, распределяя запросы между несколькими экземплярами Puma (или другими серверами приложений), что повышает масштабируемость.
Пример конфигурации Nginx для проксирования к Puma:
nginxserver {
listen 80;
server_name example.com;
location / {
proxy_pass http://localhost:3000; # Puma
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
}
}



Безопасность и дополнительные функции:

Nginx поддерживает настройку HTTPS (через SSL/TLS), защиту от атак (например, ограничение скорости запросов), кэширование и сжатие.
Puma не имеет таких встроенных возможностей и требует внешнего веб-сервера для продакшен-окружений.


Простота настройки HTTPS:

Nginx легко интегрируется с Let’s Encrypt для автоматической настройки SSL:
bashsudo certbot --nginx

Puma не работает напрямую с SSL, и настройка HTTPS через Puma сложнее.


Надёжность в продакшене:

Nginx более устойчив к высоким нагрузкам и может обрабатывать отказы серверов приложений (например, переключение на другую ноду при сбое).
Puma больше подходит для выполнения кода, а не для управления сетевыми запросами.



Когда используют Puma:

Puma используется в связке с Nginx, где Nginx обрабатывает HTTP-запросы, а Puma выполняет Ruby-код (например, для Rails-приложений).
В разработке Puma может использоваться самостоятельно, так как прост в настройке и не требует сложной конфигурации веб-сервера.

Итог:
Nginx и Puma комплементарны:

Nginx — для сетевых операций, статического контента и проксирования.
Puma — для выполнения серверного кода и обработки динамического контента.
В продакшене их обычно используют вместе: Nginx как фронтенд (прокси), а Puma как бэкенд (сервер приложений).

Вопрос 9. Балансировка нагрузки на сервера приложений (haproxy).
Ответ

Балансировка нагрузки — это процесс распределения входящих запросов между несколькими серверами (например, экземплярами Puma), чтобы оптимизировать использование ресурсов, повысить производительность и обеспечить отказоустойчивость.
HAProxy — это высокопроизводительный балансировщик нагрузки и прокси-сервер, используемый для распределения HTTP, TCP или других сетевых запросов между несколькими серверами.
Как работает HAProxy:

Приём запросов:

HAProxy принимает входящие запросы (например, HTTP на порту 80 или 443).


Распределение:

Использует алгоритмы (round-robin, leastconn, и т.д.) для передачи запросов на серверы приложений (например, Puma на разных узлах).


Проверка состояния:

Проверяет доступность серверов (health checks) и исключает недоступные из ротации.


Обработка отказов:

Перенаправляет запросы на рабочие серверы в случае сбоя одного из них.

Основные возможности HAProxy:

Алгоритмы балансировки:

Round-robin: Запросы распределяются по очереди.
Leastconn: Запросы отправляются на сервер с наименьшим числом активных соединений.
Source: Запросы от одного клиента всегда идут на один сервер (на основе IP).


Health Checks: Проверка состояния серверов (например, отправка HTTP-запросов для проверки доступности).
SSL/TLS: Поддержка HTTPS с терминацией SSL.
Логирование и мониторинг: Подробные логи и статистика (например, через Stats UI).

Пример интеграции с Puma:

Запустите несколько экземпляров Puma на разных серверах или портах:
bash# Сервер 1
puma -b tcp://192.168.1.10:3000
# Сервер 2
puma -b tcp://192.168.1.11:3000

Настройте HAProxy для распределения запросов между ними (см. конфигурацию выше).
Запустите HAProxy:
bashsudo haproxy -f /etc/haproxy/haproxy.cfg


Преимущества HAProxy:

Высокая производительность и низкое потребление ресурсов.
Гибкость: поддержка HTTP, TCP, WebSocket.
Отказоустойчивость: автоматическое переключение на рабочие серверы.
Простая настройка и масштабируемость.

Недостатки:

Требует ручной настройки и мониторинга.
Сложнее для новичков по сравнению с облачными балансировщиками (например, AWS ELB).
Не выполняет функции веб-сервера (например, не отдаёт статические файлы, как Nginx).

Альтернативы:

Nginx: Может выступать как балансировщик нагрузки:

server 192.168.1.11:3000;
}

}

Облачные решения: AWS Elastic Load Balancer, Google Cloud Load Balancing.
Traefik: Современный балансировщик с автоматическим обнаружением сервисов.

Когда использовать HAProxy:

Для высоконагруженных приложений, где требуется точная настройка балансировки.
В системах, где Nginx используется как веб-сервер, а HAProxy — для распределения нагрузки между серверами приложений.
Для TCP-балансировки (например, для баз данных или WebSocket).

Итог:
HAProxy — мощный инструмент для балансировки нагрузки, особенно в сочетании с Puma и Nginx. Он позволяет масштабировать приложение, распределяя запросы между несколькими серверами приложений, и обеспечивает отказоустойчивость.

Вопрос 11. Из чего состоит HTTP запрос?
Ответ
HTTP-запрос — это сообщение, отправляемое клиентом (например, браузером) серверу для получения или передачи данных. Он состоит из нескольких ключевых компонентов, структурированных в текстовом формате. Вот из чего состоит HTTP-запрос:

### 1. **Стартовая строка (Request Line)**  
Первая строка запроса, содержащая основную информацию о запросе. Она включает:  
- **Метод запроса**: Указывает действие, которое нужно выполнить. Основные методы:  
- `GET` — получить данные.  
- `POST` — отправить данные.  
- `PUT` — обновить данные.  
- `DELETE` — удалить данные.  
- `HEAD`, `PATCH`, `OPTIONS` и др. — менее распространённые методы.  
- **URI (Uniform Resource Identifier)**: Путь к ресурсу на сервере (например, `/api/users` или `/index.html`).  
- **Версия HTTP**: Протокол, используемый для связи (например, `HTTP/1.1`, `HTTP/2`).  

**Пример стартовой строки**:  
```
GET /api/users HTTP/1.1
```

---

### 2. **Заголовки (Headers)**  
Заголовки содержат метаданные о запросе, такие как информация о клиенте, формате данных или аутентификации. Они представляют собой пары "ключ: значение".  

#### Популярные заголовки:  
- `Host`: Доменное имя сервера (например, `example.com`).  
- `User-Agent`: Информация о клиенте (браузер, ОС, устройство).  
- `Accept`: Типы данных, которые клиент может принять (например, `application/json`, `text/html`).  
- `Content-Type`: Формат данных в теле запроса (например, `application/json` для POST).  
- `Authorization`: Данные для аутентификации (например, токен).  
- `Cookie`: Данные сессии клиента.  

**Пример заголовков**:  
```
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/91.0.4472.124
Accept: text/html,application/json
Content-Type: application/json
```

---

### 3. **Тело запроса (Request Body)**  
Содержит данные, отправляемые на сервер (например, при использовании методов `POST` или `PUT`).  
- **Необязательно**: Тело отсутствует в запросах `GET`, `HEAD`.  
- **Формат**: Зависит от `Content-Type` (например, JSON, XML, форма `application/x-www-form-urlencoded`).  

**Пример тела (для POST)**:  
```json
{
"username": "john",
"password": "secret"
}
```

---

### Полный пример HTTP-запроса:
```http
POST /api/login HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/91.0.4472.124
Content-Type: application/json
Content-Length: 53
Accept: application/json

{
"username": "john",
"password": "secret"
}
```

#### Разбор:
- **Стартовая строка**: `POST /api/login HTTP/1.1` — запрос на создание сессии.  
- **Заголовки**: Указывают сервер (`Host`), тип клиента (`User-Agent`), формат данных (`Content-Type`), и т.д.  
- **Тело**: JSON с данными для логина.  

---

### Дополнительные замечания:
- **HTTP/2 и HTTP/3**: В современных версиях HTTP запросы могут быть бинарными (вместо текстовых) и поддерживают мультиплексирование, но структура (метод, URI, заголовки, тело) остаётся схожей.  
- **Кодирование**: Заголовки и стартовая строка используют ASCII, тело может быть в любом формате (зависит от `Content-Type`).  
- **Безопасность**: Для защиты данных (особенно в теле) используется HTTPS (HTTP поверх TLS).

Вопрос 14. Что такое сессии? Для чего нужны?
Ответ
Сессия — это механизм, используемый в веб-приложениях для сохранения состояния пользователя между его HTTP-запросами, поскольку HTTP — это протокол без сохранения состояния (stateless). Сессии позволяют серверу "запомнить" пользователя и его действия в течение определённого времени.
Как работают сессии:

Создание сессии:

При первом запросе пользователя сервер генерирует уникальный идентификатор сессии (session ID).
Этот ID отправляется клиенту, обычно в виде cookie (например, session_id=abc123).


Хранение данных:

Данные сессии хранятся на сервере (в памяти, базе данных, файлах) или, реже, на клиенте (в cookie).
Session ID связывает запросы клиента с данными на сервере.


Использование:

При каждом последующем запросе клиент отправляет session ID, а сервер использует его для восстановления контекста (например, данных пользователя).


Завершение:

Сессия может быть завершена по таймауту (например, через 30 минут бездействия) или при явном выходе пользователя (logout).



Для чего нужны:

Аутентификация: Хранение информации о входе пользователя (например, "залогинен как admin").
Персонализация: Сохранение пользовательских настроек (язык, тема интерфейса).
Состояние приложения: Отслеживание временных данных (например, содержимое корзины в интернет-магазине).
Многоэтапные процессы: Поддержка прогресса в формах или wizard’ах.

Пример (Ruby on Rails):
ruby# Сохранение данных в сессии
session[:user_id] = user.id
# Получение данных
current_user = User.find(session[:user_id])
Безопасность:

Используйте HTTPS для защиты session ID.
Защищайте от CSRF-атак (например, с помощью CSRF-токенов).
Ограничивайте время жизни сессии.

Вопрос 16. Что такое crontab и для чего используются?

Crontab — это инструмент в Unix-подобных системах (Linux, macOS) для планирования и автоматического выполнения задач по расписанию. Он представляет собой файл конфигурации, где задаются команды и время их выполнения.
Как работает:

Cron — это демон (служба), который запускает задачи по расписанию.
Crontab — файл, содержащий список задач (cron jobs) с указанием времени их выполнения.
Формат строки crontab:
text* * * * * /path/to/script.sh
│ │ │ │ │
│ │ │ │ └─ День недели (0-7, где 0 или 7 — воскресенье)
│ │ │ └─ Месяц (1-12)
│ │ └─ День месяца (1-31)
│ └─ Час (0-23)
└─ Минута (0-59)


Пример:
bash# Запуск скрипта backup.sh каждый день в 2:00
0 2 * * * /usr/bin/backup.sh
Для чего используется:

Автоматизация задач:

Резервное копирование базы данных.
Очистка логов.
Отправка email-уведомлений.


Периодические задачи:

Обновление кэша.
Синхронизация данных.
Запуск аналитических отчётов.


Управление сервером:

Перезапуск сервисов.
Мониторинг системы.



Работа с crontab:

Открыть редактор crontab:
bashcrontab -e

Добавить задачу (например, запуск скрипта каждые 5 минут):
bash*/5 * * * * /path/to/script.sh

Просмотреть текущие задачи:
bashcrontab -l

Логи: Проверяйте /var/log/cron или /var/log/syslog для отладки.

Особенности:

Ограничения: Задачи выполняются в минимальной среде (нужно указывать полный путь к командам).
Альтернативы: systemd timers, anacron (для задач, не требующих строгого расписания).

Вопрос 17. Как устроен HTTP, какие есть заголовки, как работают cookies, как работает HTTPS?
Ответ
Как устроен HTTP:
HTTP (HyperText Transfer Protocol) — это протокол прикладного уровня для передачи данных между клиентом (например, браузером) и сервером. Он работает по модели "запрос-ответ".
Структура HTTP-запроса:

Стартовая строка:

Содержит метод (GET, POST, и т.д.), URI (/api/users), версию протокола (HTTP/1.1).
Пример: GET /index.html HTTP/1.1.


Заголовки: Метаданные о запросе (см. ниже).
Тело: Данные, отправляемые серверу (например, JSON в POST).

Структура HTTP-ответа:

Стартовая строка: Код состояния (200 OK, 404 Not Found) и версия протокола.

Пример: HTTP/1.1 200 OK.


Заголовки: Метаданные ответа.
Тело: Данные, возвращаемые сервером (HTML, JSON, и т.д.).

Основные заголовки:

Запросные заголовки:

Host: Доменное имя сервера (например, example.com).
User-Agent: Информация о клиенте (браузер, ОС).
Accept: Типы данных, которые клиент может принять (text/html, application/json).
Content-Type: Формат тела запроса (application/json, multipart/form-data).
Authorization: Данные для аутентификации (например, Bearer-токен).
Cookie: Данные сессии или другие cookies.


Ответные заголовки:

Content-Type: Тип возвращаемых данных (text/html, application/json).
Set-Cookie: Установка cookie на клиенте.
Cache-Control: Управление кэшированием (no-cache, max-age=3600).
Location: URL для перенаправления (используется в 301/302).


Общие заголовки:

Content-Length: Размер тела сообщения.
Connection: Управление соединением (keep-alive, close).



Как работают cookies:

Cookies — это небольшие данные, которые сервер отправляет клиенту (браузеру) для хранения и последующей отправки обратно с каждым запросом.
Механизм:

Сервер отправляет заголовок Set-Cookie в ответе:
httpSet-Cookie: session_id=abc123; Path=/; HttpOnly; Secure

Браузер сохраняет cookie и отправляет его в заголовке Cookie с каждым запросом к тому же домену:
httpCookie: session_id=abc123



Атрибуты cookie:

HttpOnly: Запрещает доступ к cookie через JavaScript (защита от XSS).
Secure: Отправляется только по HTTPS.
Path/Domain: Ограничивает область действия cookie.
Expires/Max-Age: Время жизни cookie.


Применение:

Хранение session ID.
Отслеживание пользователей (например, для аналитики).
Персонализация (настройки пользователя).



Как работает HTTPS:
HTTPS — это HTTP, работающий поверх шифрованного соединения (TLS/SSL), обеспечивающий безопасность данных.
Механизм:

Установление соединения:

Клиент и сервер выполняют TLS handshake:

Клиент запрашивает сертификат у сервера.
Сервер предоставляет SSL-сертификат, подписанный доверенным центром (CA).
Клиент проверяет сертификат и договаривается о ключе шифрования.




Шифрование:

Все данные (запросы и ответы) шифруются с использованием симметричного ключа, согласованного во время handshake.


Аутентификация:

Сертификат подтверждает, что сервер — это тот, за кого он себя выдаёт.


Целостность:

TLS гарантирует, что данные не были изменены в процессе передачи.



Преимущества HTTPS:

Защита от перехвата данных (например, паролей, session ID).
Защита от атак "человек посередине" (MITM).
Улучшение SEO (Google отдаёт предпочтение HTTPS-сайтам).

Пример настройки HTTPS (Nginx):
nginxserver {
listen 443 ssl;
server_name example.com;
ssl_certificate /etc/letsencrypt/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/privkey.pem;
location / {
proxy_pass http://localhost:3000; # Puma
}
}
Итог:

HTTP: Протокол запрос-ответ с тремя частями (стартовая строка, заголовки, тело).
Заголовки: Управляют метаданными, форматом и поведением запроса/ответа.
Cookies: Хранят состояние (например, session ID) для взаимодействия между запросами.
HTTPS: Шифрует HTTP-трафик через TLS/SSL для безопасности.

Вопрос 20. Назовите отличия протокола TCP и UDP.


Ответ 
Протокол TCP (Transmission Control Protocol) – это сетевой протокол, который «заточен» под соединение. Иными словами, прежде, чем начать обмен данными, данному протоколу требуется установить соединение между двумя хостами. Данный протокол имеет высокую надежность, поскольку позволяет не терять данные при передаче, запрашивает подтверждения о получении от принимающей стороны и в случае необходимости отправляет данные повторно. При этом отправляемые пакеты данных сохраняют порядок отправки, то есть можно сказать, что передача данных упорядочена. Минусом данного протокола является относительно низкая скорость передачи данных, за счет того что выполнение надежной и упорядоченной передачи занимает больше времени, чем в альтернативном протоколе UDP.

Протокол UDP (User Datagram Protocol), в свою очередь, более прост. Для передачи данных ему не обязательно устанавливать соединение между отправителем и получателем. Информация передается без предварительной проверки готовности принимающей стороны. Это делает протокол менее надежным – при передаче некоторые фрагменты данных могут теряться. Кроме того, упорядоченность данных не соблюдается – возможен непоследовательный прием данных получателем. Зато скорость передачи данных по данному транспортному протоколу будет более высокой.

Вопрос 21. Что такое RPC?


Ответ 
RPC (от англ. Remote Procedure Call, RPC) Удалённый вызов процедур, реже Вызов удалённых процедур — класс технологий, позволяющих компьютерным программам вызывать функции или процедуры в другом адресном пространстве (на удалённых компьютерах, либо в независимой сторонней системе на том же устройстве). Обычно реализация RPC-технологии включает в себя два компонента: сетевой протокол для обмена в режиме клиент-сервер и язык сериализации объектов (или структур, для необъектных RPC).
