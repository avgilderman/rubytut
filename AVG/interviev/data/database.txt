Вопросы по базам данных


Вопрос 1. Что такое реляционная база данных?


Ответ 
Реляционная база данных — это набор данных с предопределенными связями между ними. Эти данные организованны
в виде набора таблиц, состоящих из столбцов и строк. В таблицах хранится информация об объектах, представленных
в базе данных. В каждом столбце таблицы хранится определенный тип данных, в каждой ячейке — значение атрибута.
Каждая строка таблицы представляет собой набор связанных значений, относящихся к одному объекту или сущности.


Вопрос 2. Что такое таблица, кортеж? Что такое primary key?


Ответ 
Таблица — это набор элементов данных (значений), использующий модель вертикальных столбцов
(имеющих уникальное имя) и горизонтальных строк. Таблица содержит определенное число столбцов, но может иметь
любое количество строк.
Каждая строка однозначно определяется одним или несколькими уникальными значениями,
которые принимают её ячейки из определенного подмножества столбцов. Подмножество столбцов,
которое уникально идентифицирует строку, называется первичным ключом(primary key).

- Primary key не позволяет создавать одинаковых записей (строк) в таблице;
- PK обеспечивают логическую связь между таблицами одной базы данных.

По соглашению Rails предполагает, что для первичного ключа используется столбец _id_ в таблице,
который автоматически создается для каждой вашей записи.

**Кортеж** - это набор именованных значений заданного типа.

Вопрос 3. Как реализованы связи между таблицами? Что такое foreign key?


Ответ 
Между двумя или более таблицами базы данных могут существовать отношения подчиненности. Отношения подчиненности
определяют, что для каждой записи главной таблицы может существовать одна или несколько записей в подчиненной таблице.

Существует три разновидности связей между таблицами базы данных:

* «один-ко-многим»,

* «один-к-одному»,

* «многие-ко-многим».

Внешний ключ **Foreign key**, кратко FK. Обеспечивает однозначную логическую связь, между таблицами одной БД.
Для обеспечения ссылочной целостности в дочерней таблице создается внешний ключ. Во внешний ключ входят
поля связи дочерней таблицы. Для связей типа "один-ко-многим" внешний ключ по составу полей должен совпадать
с первичным ключом родительской таблицы.

Например, есть две таблицы А и В. В таблице А (обувь), есть первичный ключ: размер,
в таблице В (цвет) должна быть колонка с названием размер. В этой таблице «размер»
это и будет внешний ключ для логической связи таблиц В и А.

По соглашению Rails предполагает, что столбец, используемый для хранения внешнего ключа в этой модели, имеет имя модели с добавленным суффиксом _id_


Вопрос 4. Как работает SELECT оператор?


Ответ 
SELECT - оператор запроса, возвращающий набор данных (выборку) из базы данных.

Оператор SELECT состоит из нескольких предложений (разделов):

Сам **SELECT** определяет список возвращаемых столбцов (как существующих, так и вычисляемых), их имена,
ограничения на уникальность строк в возвращаемом наборе, ограничения на количество строк в возвращаемом наборе;

**FROM** задаёт табличное выражение, которое определяет базовый набор данных для применения операций, определяемых
в других предложениях оператора;

**WHERE** задает ограничение на строки табличного выражения из предложения FROM;

**GROUP BY** объединяет ряды, имеющие одинаковое свойство с применением агрегатных функций

**HAVING** выбирает среди групп, определенных параметром GROUP BY

**ORDER BY** задает критерии сортировки строк; отсортированные строки передаются в точку вызова.

Синтаксис оператора SELECT:

```sql
SELECT <column_list> 
FROM <table_name> 
[WHERE <условие>] 
[GROUP BY <условие>] 
[HAVING <условие>] 
[ORDER BY <условие>] 
```


Вопрос 5. Какие бывают виды JOIN? Как каждый работает?


Ответ 
INNER JOIN - оператор внутреннего соединения, соединяет две таблицы. Выбираются только совпадающие данные из
объединяемых таблиц. 

OUTER JOIN - существует два типа внешнего объединения: LEFT OUTER JOIN и RIGHT OUTER JOIN. 
Работают они одинаково, разница заключается в том что LEFT - указывает что "внешней" таблицей будет находящаяся
слева, а RIGHT - справа. Выбираются все данные из внешней таблицы + совпадения из второй таблицы.

Cross/Full Join - FULL JOIN возвращает объединение объединений LEFT и RIGHT таблиц, комбинируя результат двух запросов.
CROSS JOIN возвращает перекрестное объединение двух таблиц. Результатом будет выборка всех записей первой таблицы
объединенная с каждой строкой второй таблицы. Важным моментом является то, что для кросса не нужно указывать
условие объединения.

Вопрос 6. Как работают INSERT, UPDATE, DELETE операторы?


Ответ 
INSERT — оператор, который позволяет добавить строки в таблицу, заполняя их значениями.
Значения можно вставлять перечислением с помощью слова values и перечислив их в круглых скобках через запятую или
оператором SELECT.

Синтаксис:

```sql
INSERT INTO table_name (column1, column2, column3, ...)
VALUES (value1, value2, value3, ...);
```

UPDATE — оператор, позволяющий обновить значения в заданных столбцах таблицы.

Синтаксис:

```sql
UPDATE table_name
SET column1 = value1, column2 = value2, ...
WHERE condition;
```

DELETE — операция удаления записей из таблицы. Критерий отбора записей для удаления определяется выражением WHERE.
В случае, если критерий отбора не определён, выполняется удаление всех записей.

Синтаксис:

```sql
DELETE FROM table_name WHERE condition;
```



Вопрос 7. Что такое индексы? Для чего используются? Плюсы, минусы?


Ответ 
Индекс — объект базы данных, создаваемый с целью повышения производительности поиска данных. Таблицы в базе
данных могут иметь большое количество строк, которые хранятся в произвольном порядке, и их поиск по заданному
критерию путём последовательного просмотра таблицы строка за строкой может занимать много времени.
Индекс формируется из значений одного или нескольких столбцов таблицы и указателей на соответствующие строки
таблицы и, таким образом, позволяет искать строки, удовлетворяющие критерию поиска.

Ускорение работы с использованием индексов достигается в первую очередь за счёт того, что индекс имеет структуру,
оптимизированную под поиск.

Для оптимальной производительности запросов индексы обычно создаются на тех столбцах таблицы,
которые часто используются в запросах.  Однако увеличение числа индексов замедляет операции добавления,
обновления, удаления строк таблицы, поскольку при этом приходится обновлять сами индексы. Кроме того, индексы
занимают дополнительный объем памяти.


Вопрос 8. Какие виды индексов бывают?

* Возрастающие

* убывающие

* Некластерный индекс

* Кластерный индекс

* B+-деревья

* Хеши

#### По количественному составу
* Простой индекс (индекс с одним ключом)

* Главный индекс (индекс по первичному ключу)

#### По характеристике содержимого

* Уникальный индекс

* Разреженный индекс (NoSQL)

* Пространственный индекс

* Составной пространственный индекс

#### По покрытию индексируемого содержимого

Вопрос 9. Что такое полнотекстовый поиск?
Ответ
Полнотекстовый поиск в базах данных — это метод поиска, который позволяет находить данные, анализируя весь текст в документах или записях, а не только отдельные поля или ключевые слова. Он используется для обработки текстовых данных, таких как статьи, описания, комментарии, и ориентирован на поиск по содержимому, включая слова, фразы, их формы или даже синонимы.
Основные особенности полнотекстового поиска:

Индексация текста: База данных создаёт специальный индекс, содержащий слова из текстовых полей, что ускоряет поиск. Например, слова разбиваются на токены, исключаются стоп-слова (предлоги, союзы), и учитываются словоформы (например, "бегать", "бегу", "бег").
Поиск по ключевым словам и фразам: Пользователь может искать точные фразы, части слов или комбинации слов с использованием логических операторов (AND, OR, NOT).
Ранжирование результатов: Найденные записи сортируются по релевантности, учитывая, например, частоту вхождения ключевых слов или их близость в тексте.
Поддержка естественного языка: Некоторые системы поддерживают поиск с учётом синонимов, морфологии или даже семантического смысла запроса.

Примеры технологий:

В реляционных СУБД: PostgreSQL (с модулем tsvector и tsquery), MySQL (с FULLTEXT индексами).
В NoSQL: MongoDB, Elasticsearch, Solr, которые специализируются на полнотекстовом поиске.
Пример в PostgreSQL:
sqlSELECT * FROM articles 
WHERE to_tsvector('russian', content) @@ to_tsquery('russian', 'кот & собака');
Этот запрос ищет документы, содержащие слова "кот" и "собака" в поле content.

Преимущества:

Быстрый поиск по большим объёмам текста.
Гибкость: поддержка сложных запросов, включая частичное совпадение или поиск по словоформам.
Удобство для пользователей: можно искать, как в поисковых системах (например, Google).

Недостатки:

Требует больше ресурсов для создания и хранения индексов.
Сложность настройки для языков с богатой морфологией, таких как русский.
Не всегда эффективен для точных совпадений (например, поиск по ID).

Полнотекстовый поиск широко применяется в веб-приложениях, поисковых системах, аналитических системах и любых задачах, где нужно искать по содержимому текста.

Вопрос 10. Что такое транзакции?

Ответ 

Транза́кция — группа последовательных операций с базой данных, 
которая представляет собой логическую единицу работы с данными.
Транзакция может быть выполнена либо целиком и успешно (**Commit**),
соблюдая целостность данных и независимо от параллельно идущих других транзакций,
либо не выполнена вообще (**Rollback**), и тогда она не должна произвести никакого эффекта.

Вопрос 11. Расскажите об уровнях изолированности транзакции

Ответ 

**Уровень изолированности транзакций** — условное значение,
определяющее, в какой мере в результате выполнения логически параллельных транзакций в СУБД
допускается получение несогласованных данных. Шкала уровней изолированности транзакций
содержит ряд значений, проранжированных от наинизшего до наивысшего;
более высокий уровень изолированности соответствует лучшей согласованности данных, 
но его использование может снижать количество физически параллельно выполняемых транзакций.

#### Проблемы параллельного доступа с использованием транзакций

При параллельном выполнении транзакций возможны следующие проблемы:

* потерянное обновление (англ. lost update)

* «грязное» чтение (англ. dirty read)

* неповторяющееся чтение (англ. non-repeatable read)

* фантомное чтение (англ. phantom reads)

#### Уровни изоляции

Под «уровнем изоляции транзакций» понимается степень обеспечиваемой внутренними механизмами СУБД
(то есть не требующей специального программирования) защиты от всех или некоторых видов
вышеперечисленных несогласованности данных, возникающих при параллельном выполнении транзакций.

Первый из них является самым слабым, последний — самым сильным,
каждый последующий включает в себя все предыдущие.

* Read uncommitted (чтение незафиксированных данных)
* Read committed (чтение фиксированных данных)
* Repeatable read (повторяемость чтения)
* Serializable (упорядочиваемость)

https://ru.wikipedia.org/wiki/Уровень_изолированности_транзакций


Вопрос 12. Что такое блокировочные и версионные СУБД?
Ответ
Блокировочные и версионные СУБД — это два подхода к управлению параллельным доступом к данным в системах управления базами данных (СУБД). Они решают проблему обеспечения согласованности данных при одновременной работе нескольких пользователей или транзакций. Рассмотрим их подробнее:

### 1. **Блокировочные СУБД** (Lock-Based DBMS)
Блокировочные СУБД используют механизм блокировок для предотвращения конфликтов между транзакциями, когда несколько пользователей пытаются одновременно читать или изменять данные.

#### Как работает:
- **Блокировки**: Перед доступом к данным (чтение или запись) транзакция "захватывает" блокировку на соответствующий объект (например, строку, таблицу). Это предотвращает изменение данных другими транзакциями, пока блокировка не снята.
- **Типы блокировок**:
- **Shared Lock** (разделяемая): Позволяет нескольким транзакциям читать данные, но запрещает их изменение.
- **Exclusive Lock** (эксклюзивная): Дает одной транзакции полный контроль над данными (чтение и запись), блокируя доступ другим.
- **Механизмы**:
- Двухфазное блокирование (2PL): Все блокировки захватываются на фазе роста, а снимаются на фазе завершения.
- Управление конфликтами: Если транзакция не может получить блокировку, она ждёт (или может быть прервана для избежания взаимоблокировок).

#### Примеры СУБД:
- PostgreSQL, MySQL (с движком InnoDB), Oracle, SQL Server.

#### Преимущества:
- Простота реализации и понимания.
- Гарантирует строгую согласованность данных.
- Хорошо подходит для систем с низким уровнем конкуренции.

#### Недостатки:
- **Взаимоблокировки** (deadlocks): Возможны ситуации, когда две транзакции ждут друг друга.
- Низкая производительность при высокой конкуренции, так как транзакции могут долго ждать освобождения блокировок.
- Ограниченная масштабируемость при большом числе параллельных операций.

---

### 2. **Версионные СУБД** (Versioning DBMS, или MVCC — Multi-Version Concurrency Control)
Версионные СУБД используют механизм многоверсионности, при котором для каждой транзакции создаётся "снимок" данных, чтобы избежать конфликтов без блокировки.

#### Как работает:
- **Многоверсионность**: Вместо блокировки данных для чтения, СУБД сохраняет разные версии строк. Каждая транзакция видит данные, соответствующие её "точке во времени" (snapshot).
- **Чтение без блокировок**: Транзакции, читающие данные, не блокируют записи, так как работают с их копиями (версиями).
- **Запись**: При изменении данных создаётся новая версия строки, а старая остаётся доступной для других транзакций, пока они не завершатся.
- **Очистка**: Старые версии данных удаляются (процесс "vacuum" в PostgreSQL), когда они больше не нужны.

#### Примеры СУБД:
- PostgreSQL, Oracle, MySQL (InnoDB), Firebird, CouchDB.
- PostgreSQL, например, использует MVCC, где каждая строка хранит информацию о транзакции, создавшей или изменившей её.

#### Примеры в PostgreSQL:
- Транзакция 1 читает строку, пока Транзакция 2 изменяет её. Транзакция 1 видит старую версию строки, а Транзакция 2 создаёт новую.

#### Преимущества:
- Высокая производительность при чтении, так как нет блокировок для операций чтения.
- Меньше конфликтов при параллельной работе.
- Лучшая масштабируемость для систем с большим числом одновременных запросов.

#### Недостатки:
- Увеличение объёма хранимых данных из-за сохранения старых версий.
- Необходимость периодической очистки старых версий (например, `VACUUM` в PostgreSQL).
- Сложность реализации и настройки.

---

### Сравнение:
| Характеристика            | Блокировочные СУБД          | Версионные СУБД (MVCC)       |
|---------------------------|-----------------------------|------------------------------|
| **Механизм**              | Блокировки                 | Многоверсионность            |
| **Чтение**                | Может блокироваться        | Без блокировок (снимки)      |
| **Запись**                | Блокирует данные           | Создаёт новую версию         |
| **Производительность**    | Ниже при высокой конкуренции | Выше при параллельных чтениях |
| **Сложность**             | Проще                      | Сложнее                      |
| **Риски**                 | Взаимоблокировки           | Накопление старых версий     |

### Итог:
- **Блокировочные СУБД** лучше подходят для систем с низкой конкуренцией и строгой необходимостью в согласованности.
- **Версионные СУБД (MVCC)** предпочтительны для приложений с высокой нагрузкой на чтение и параллельные операции, таких как веб-приложения или аналитические системы.

Многие современные СУБД (например, PostgreSQL, MySQL InnoDB) используют MVCC как основной механизм, иногда комбинируя его с блокировками для определённых операций.

Вопрос 15. Типичные bottle necks?
Ответ Узкие места в СУБД — это факторы, ограничивающие производительность системы. Типичные bottle necks включают:

I/O (ввод/вывод):

Медленные дисковые операции из-за большого объёма данных или недостаточной скорости дисков (например, HDD вместо SSD).
Решение: Использование SSD, увеличение кэша, оптимизация запросов.


CPU:

Высокая нагрузка на процессор из-за сложных запросов, сортировок, агрегаций или недостаточной оптимизации индексов.
Решение: Оптимизация запросов, добавление индексов, распараллеливание задач.


Память:

Недостаток оперативной памяти для кэширования данных или выполнения операций, что приводит к частым обращениям к диску.
Решение: Увеличение объёма RAM, настройка параметров кэширования (например, work_mem в PostgreSQL).


Блокировки:

Конфликты между транзакциями в блокировочных СУБД, особенно при высокой конкуренции.
Решение: Использование MVCC, оптимизация транзакций, снижение времени удержания блокировок.


Плохо оптимизированные запросы:

Неэффективные SQL-запросы, такие как сканирование всей таблицы вместо использования индексов, избыточные JOIN’ы.
Решение: Анализ плана запросов (EXPLAIN), создание подходящих индексов, переписывание запросов.


Сетевые задержки:

Медленная передача данных между клиентом и сервером базы данных.
Решение: Оптимизация сетевой инфраструктуры, использование локальных серверов или кэширования.


Недостаток индексов или их избыток:

Отсутствие индексов замедляет поиск, а слишком много индексов увеличивает время записи.
Решение: Анализ использования индексов, удаление неиспользуемых.


Ограничения конфигурации СУБД:

Неправильные настройки параметров (например, размер буферного пула, лимиты соединений).
Решение: Тюнинг конфигурации под нагрузку.

Вопрос 16. Объяснить разницу между SQL Injection and CSS Injection?
Ответ 
SQL Injection:

Что это: Атака, при которой злоумышленник внедряет вредоносный SQL-код в запрос, чтобы получить несанкционированный доступ к данным, изменить их или выполнить команды в базе данных.
Как работает:

Злоумышленник вводит SQL-код в поля ввода (например, формы логина), которые напрямую включаются в SQL-запрос без проверки.
Пример: Поле ввода логина user' OR '1'='1 в запросе SELECT * FROM users WHERE username = '[ввод]' позволяет обойти авторизацию.


Последствия:

Утечка данных (например, паролей).
Изменение или удаление данных.
Выполнение административных команд (например, DROP TABLE).


Защита:

Использование параметризованных запросов или подготовленных выражений.
Экранирование пользовательского ввода.
Ограничение прав доступа к базе данных.



CSS Injection (Cross-Site Scripting, XSS):

Что это: Атака, при которой злоумышленник внедряет вредоносный JavaScript (или другой клиентский код) в веб-страницу, чтобы выполнить его в браузере пользователя.
Как работает:

Вредоносный код вводится через поля ввода, URL или другие точки, где пользовательский ввод отображается без фильтрации.
Пример: Ввод alert('Hacked!') в форму комментариев, которая отображается на странице.


Последствия:

Кража cookies, сессий или личных данных пользователя.
Перенаправление на фишинговые сайты.
Выполнение любых действий от имени пользователя.


Защита:

Экранирование пользовательского ввода (например, преобразование < в &lt;).
Использование заголовков Content Security Policy (CSP).
Валидация и фильтрация ввода на сервере.



Ключевая разница:

Цель:

SQL Injection нацелена на серверную часть (базу данных).
CSS Injection (XSS) нацелена на клиентскую часть (браузер пользователя).


Технологии:

SQL Injection использует SQL-код.
CSS Injection использует JavaScript, HTML или CSS.


Место атаки:

SQL Injection происходит в серверных запросах к базе данных.
CSS Injection — в отображаемом контенте веб-страницы.

Вопрос 17. Что такое BETWEEN?
Ответ
BETWEEN — это оператор в SQL, используемый в условии WHERE для выбора значений, находящихся в заданном диапазоне (включительно).
Синтаксис:
sqlSELECT column_name
FROM table_name
WHERE column_name BETWEEN value1 AND value2;
Как работает:

Проверяет, попадает ли значение столбца в диапазон от value1 до value2 (включая границы).
Эквивалентно комбинации условий: column_name >= value1 AND column_name <= value2.
Работает с числами, датами, строками (в зависимости от типа данных столбца).

Пример:
sqlSELECT * FROM employees
WHERE salary BETWEEN 50000 AND 70000;

Выбирает сотрудников с зарплатой от 50,000 до 70,000 включительно.

Особенности:

Включительность: BETWEEN включает граничные значения (value1 и value2).
Производительность: Может быть оптимизирован индексами, если они есть.
Ограничения: Не подходит для сложных условий, требующих исключения границ.

Пример с датами:
sqlSELECT * FROM orders
WHERE order_date BETWEEN '2023-01-01' AND '2023-12-31';

Выбирает заказы за 2023 год.

Вопрос 18. Чем Like отличается от Ilike?
Ответ
LIKE:

Оператор в SQL для поиска строк по шаблону с учётом регистра (case-sensitive).
Используется в условии WHERE для поиска подстрок с использованием символов:

% — любое количество символов.
_ — один символ.


Пример:
sqlSELECT * FROM users
WHERE username LIKE 'John%';

Найдёт John, Johnny, но не john или JOHN.



ILIKE:

Оператор, специфичный для некоторых СУБД (например, PostgreSQL), для поиска строк по шаблону без учёта регистра (case-insensitive).
Работает аналогично LIKE, но игнорирует различия между заглавными и строчными буквами.
Пример:
sqlSELECT * FROM users
WHERE username ILIKE 'John%';

Найдёт John, john, JOHN, Johnny, joHnny и т.д.



Ключевая разница:

Чувствительность к регистру:

LIKE — чувствителен к регистру.
ILIKE — нечувствителен к регистру.


Поддержка:

LIKE поддерживается во всех SQL-стандартных СУБД.
ILIKE — расширение, характерное для PostgreSQL. В других СУБД (например, MySQL) эквивалент достигается через функции вроде LOWER() или UPPER():
sqlSELECT * FROM users
WHERE LOWER(username) LIKE LOWER('John%');




Примечания:

ILIKE может быть чуть медленнее, так как игнорирование регистра требует дополнительной обработки.
Для улучшения производительности используйте индексы (например, CREATE INDEX ... USING gin (column gin_trgm_ops) в PostgreSQL для поиска по шаблону).

Вопрос 25. Системы репликации, что это и зачем нужно?
Ответ
### Что такое системы репликации в базах данных?

Системы репликации в базах данных — это технологии и процессы, которые обеспечивают копирование данных из одной базы данных (основной, или master) в одну или несколько других баз данных (реплик, или slaves/replicas). Репликация позволяет создавать и поддерживать актуальные копии данных на разных серверах или узлах.

### Основные типы репликации:
1. **Мастер-реплика (Master-Slave)**:
- Один сервер (мастер) обрабатывает все операции записи, а реплики синхронизируются с мастером, копируя изменения.
- Реплики обычно используются только для чтения.
- Пример: MySQL с асинхронной репликацией.

2. **Мастер-мастер (Master-Master)**:
- Все узлы могут принимать операции записи и чтения, синхронизируя изменения между собой.
- Более сложная настройка из-за потенциальных конфликтов данных.
- Пример: PostgreSQL с BDR (Bi-Directional Replication).

3. **Асинхронная репликация**:
- Изменения на мастере передаются на реплики с небольшой задержкой.
- Простота реализации, но есть риск потери данных при сбое мастера.
- Пример: PostgreSQL Streaming Replication (асинхронный режим).

4. **Синхронная репликация**:
- Изменения на мастере подтверждаются только после записи на все реплики.
- Высокая надёжность, но может снижать производительность из-за задержек.
- Пример: PostgreSQL с синхронной репликацией.

5. **Логическая репликация**:
- Копируются только определённые изменения (например, конкретные таблицы или строки), а не весь физический журнал транзакций.
- Пример: PostgreSQL Logical Replication.

6. **Физическая репликация**:
- Копируются все данные на уровне блоков или файлов.
- Пример: MySQL Binary Log, PostgreSQL WAL (Write-Ahead Log).

### Зачем нужна репликация?

1. **Высокая доступность (High Availability)**:
- Если мастер выходит из строя, реплика может взять на себя его функции (failover).
- Пример: В PostgreSQL можно настроить автоматическое переключение на реплику с помощью инструментов вроде Patroni.

2. **Балансировка нагрузки**:
- Запросы на чтение распределяются между репликами, снижая нагрузку на мастер.
- Пример: Веб-приложение направляет аналитические запросы на реплики, а обновления — на мастер.

3. **Резервное копирование**:
- Реплики могут использоваться для создания резервных копий без остановки основной базы.
- Пример: Создание бэкапов на реплике в MySQL.

4. **Географическое распределение**:
- Реплики размещаются в разных регионах, чтобы уменьшить задержки для пользователей.
- Пример: Реплики в разных дата-центрах для глобальных приложений.

5. **Обеспечение отказоустойчивости**:
- Репликация защищает от потери данных при сбоях оборудования или программного обеспечения.
- Пример: Синхронная репликация в Oracle Data Guard.

6. **Тестирование и аналитика**:
- Реплики могут использоваться для аналитических запросов или тестирования без влияния на основную базу.
- Пример: Запуск тяжёлых отчётов на реплике в SQL Server.

### Примеры реализации:
- **PostgreSQL**: Использует WAL (Write-Ahead Log) для физической и логической репликации. Поддерживает как синхронную, так и асинхронную репликацию.
```sql
-- Настройка стриминговой репликации в postgresql.conf
wal_level = replica
max_wal_senders = 10
```
- **MySQL**: Использует бинарные логи (binlog) для передачи изменений на реплики.
```sql
-- Настройка реплики
CHANGE MASTER TO MASTER_HOST='master_ip', MASTER_USER='replica_user', MASTER_PASSWORD='password';
```
- **MongoDB**: Репликация через Replica Sets, где есть первичный узел и вторичные, синхронизирующиеся через oplog.

### Преимущества репликации:
- Увеличение надёжности и отказоустойчивости.
- Повышение производительности за счёт распределения нагрузки.
- Поддержка географически распределённых систем.
- Минимизация простоев при сбоях.

### Недостатки:
- **Сложность настройки**: Требует тщательной конфигурации и мониторинга.
- **Задержки в асинхронной репликации**: Возможны временные несоответствия данных.
- **Конфликты в мастер-мастер**: Требуется механизм разрешения конфликтов.
- **Ресурсы**: Реплики требуют дополнительного оборудования и обслуживания.

### Итог:
Репликация — это ключевой механизм для обеспечения масштабируемости, отказоустойчивости и высокой доступности в современных базах данных. Выбор типа репликации зависит от требований приложения: синхронная для критически важных систем, асинхронная для высокой производительности, логическая для гибкости.


Вопрос 26. PgQ (другие очереди)?

Ответ 

PgQ — это еще одна система очередей, написаная skytools на базе PostgreSql. 
Если написать руками очередь на БД, то она будет работать медленно и создавать большую нагрузку. 
В PgQ удалось избежать этого за счет использования «особой PostgreSql магии». 
PgQ — транзакционная очередь, что гарантирует, что вы увидите каждой событией хотя бы один раз.

Особенностью PgQ является то, что события из нее достаются пачками (batch). 
Поэтому надо быть внимательным, чтобы не отреагировать на одно и то же событие несколько раз
(например, если обработчик собыий аварийно завершился, перед выходом стоит все необработанные события
отправить на повтор и закрыть пакет).


Вопрос 27. Что такое синхронные и асинхронные операции?
Ответ
Синхронные и асинхронные операции — это два подхода к выполнению задач в программировании и базах данных, которые отличаются по способу обработки запросов и управлению временем ожидания. Рассмотрим их применительно к базам данных и в общем контексте.

### 1. **Синхронные операции**
Синхронные операции выполняются последовательно: вызывающая сторона (например, приложение или пользователь) ждёт завершения операции, прежде чем продолжить выполнение следующей задачи.

#### Характеристики:
- **Блокирующий режим**: Выполнение программы приостанавливается, пока операция не завершится.
- **Последовательность**: Следующая операция начинается только после завершения текущей.
- **Пример в базах данных**:
- В синхронной репликации (например, в PostgreSQL) транзакция на главном сервере (master) подтверждается только после того, как все изменения записаны на реплики. Это гарантирует, что данные на мастере и репликах всегда согласованы.
- SQL-запрос: Клиент отправляет запрос `INSERT`, и приложение ждёт, пока база данных не завершит запись и не вернёт подтверждение.
- **Пример кода (общий контекст)**:
```python
# Синхронный запрос к базе данных
import sqlite3
conn = sqlite3.connect('example.db')
cursor = conn.cursor()
cursor.execute("SELECT * FROM users")  # Программа ждёт завершения запроса
result = cursor.fetchall()
print(result)
```

#### Преимущества:
- Гарантия завершения операции перед продолжением.
- Простота реализации и отладки (логика линейна).
- Полная согласованность данных в базах данных (особенно в синхронной репликации).

#### Недостатки:
- Медленнее, так как программа простаивает во время ожидания.
- Проблемы с масштабируемостью при высокой нагрузке.
- В базах данных: увеличение задержек из-за ожидания подтверждения от реплик.

---

### 2. **Асинхронные операции**
Асинхронные операции позволяют выполнять задачи без блокировки вызывающей стороны. Программа продолжает выполнение других задач, пока операция не завершится, а результат обрабатывается позже (например, через callback, promise или async/await).

#### Характеристики:
- **Неблокирующий режим**: Вызывающая сторона не ждёт завершения операции, а продолжает выполнение.
- **Параллелизм**: Можно запускать несколько операций одновременно, обрабатывая их результаты по мере завершения.
- **Пример в базах данных**:
- В асинхронной репликации изменения с мастера передаются на реплики с небольшой задержкой. Мастер подтверждает транзакцию, не дожидаясь реплик, что ускоряет запись, но может привести к временной несогласованности.
- Асинхронные запросы: Клиент отправляет SQL-запрос и продолжает работу, получая результат через callback или другой механизм.
- **Пример кода (общий контекст)**:
```python
# Асинхронный запрос с использованием async/await
import asyncio
import aiosqlite

async def fetch_data():
async with aiosqlite.connect('example.db') as db:
  async with db.execute('SELECT * FROM users') as cursor:
      rows = await cursor.fetchall()  # Ожидание результата без блокировки
      print(rows)

asyncio.run(fetch_data())
```

#### Преимущества:
- Высокая производительность при большом количестве операций, так как нет простоя.
- Лучшая масштабируемость для высоконагруженных систем.
- В базах данных: ускорение записи за счёт отсутствия ожидания реплик.

#### Недостатки:
- Сложность реализации: требует управления асинхронными потоками (callbacks, promises, async/await).
- Возможны временные несоответствия данных (в асинхронной репликации).
- Труднее отлаживать из-за нелинейного выполнения.

---

### Сравнение синхронных и асинхронных операций

| Характеристика             | Синхронные операции          | Асинхронные операции         |
|----------------------------|------------------------------|------------------------------|
| **Режим выполнения**       | Блокирующий                 | Неблокирующий               |
| **Ожидание результата**    | Ждёт завершения             | Продолжает выполнение       |
| **Сложность кода**         | Простая, линейная           | Сложнее (асинхронные механизмы) |
| **Производительность**     | Медленнее при высокой нагрузке | Быстрее при высокой нагрузке |
| **Согласованность данных** | Высокая (в базах данных)    | Может быть временная несогласованность |
| **Применение**             | Простые задачи, строгая согласованность | Высоконагруженные системы, масштабируемость |

---

### Применение в базах данных
- **Синхронная репликация**:
- Используется, когда важна полная согласованность данных (например, в банковских системах).
- Пример: PostgreSQL с параметром `synchronous_commit = on` и `synchronous_standby_names`.
```sql
-- Настройка синхронной репликации
ALTER SYSTEM SET synchronous_standby_names = 'replica1';
```
- **Асинхронная репликация**:
- Подходит для систем, где важна скорость записи, а временная несогласованность допустима (например, аналитические системы).
- Пример: MySQL с асинхронной репликацией через binlog.
```sql
-- Настройка асинхронной реплики
CHANGE MASTER TO MASTER_HOST='master_ip', MASTER_LOG_FILE='binlog.000001';
```

---

### Общий контекст
- **Синхронные операции**: Подходят для задач, где важен порядок выполнения и немедленный результат (например, последовательная обработка транзакций).
- **Асинхронные операции**: Идеальны для высоконагруженных приложений, таких как веб-серверы, где нужно обрабатывать множество запросов одновременно (например, загрузка данных с API или обработка событий).
